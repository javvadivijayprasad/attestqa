# attestqa — the product

*Status: design, agreed 2026-10-09. Runtime frozen at `f2771d4` (`corpus-2026-10-07`). This page records the decisions behind the desktop product so the code that follows has something to be checked against.*

---

## One sentence

attestqa is an open-source Windows desktop app: you open a website, point it at a model your company already pays for, and it tests the site end to end — writing ordinary Playwright code into a folder you own, and refusing, in code, to make a failing test pass by weakening it.

## What it is not

It is not a chat window that happens to write tests, and it is not a cloud service that keeps your tests in a proprietary model and rents you a runner. Both of those exist. The first produces tests nobody can audit; the second produces tests nobody can leave with. attestqa's deliverable is code, and its differentiator is the governance that produced it.

---

## 1. The three modes

Every session is in exactly one mode. The mode decides what the agent may read, what counts as the oracle, and what the report can claim.

| Mode | Input | Oracle (what "correct" means) | Output | Report may say |
|---|---|---|---|---|
| **Explore** | A URL and a login | None. The agent is describing, not judging. | `features/*.feature` drafts, a site map, a list of observed behaviours and questions | "Here is what the site does." Never "passed" or "bug". |
| **Specify** | A story (ADO, Jira, a pasted paragraph, a `.feature` the user wrote) | The story's acceptance criteria | `features/`, `tests/*.spec.ts`, `pages/*.page.ts` via bdd2pw | "AC-3 is covered by test X." Not yet "passed". |
| **Attest** | A suite that exists | The suite's assertions, as written | A ledger-counted run report; bug records for failures the human confirms | "12 passed, 2 failed, 1 quarantined — and here is the ledger." |

**The oracle principle.** The agent never supplies its own oracle. In Explore it has none and says so; in Specify the oracle is the story; in Attest the oracle is the assertion already in the file. This is the single rule that makes the weakening finding (docs/WEAKENING.md) enforceable: a model that cannot decide what "correct" means cannot decide a failing test is wrong.

Explore → Specify → Attest is the natural path for a new site, but each mode stands alone. A team with a mature suite starts in Attest; a team with good stories starts in Specify.

## 2. What lands on the user's disk

Everything the app builds is a regular Playwright project in a folder the user chose:

```
my-site-tests/
  features/            Gherkin, derived from the story or from exploring
  tests/*.spec.ts      generated by bdd2pw — plain @playwright/test
  pages/*.page.ts      page objects, same
  playwright.config.ts
  package.json
  ai-quality.config.yaml   policy: scope, provider, what the agent may touch
  .aqa/runs/<id>/events.jsonl   the ledger, one file per run
```

`npx playwright test` runs the suite with attestqa uninstalled. Commit it to the team's repo, run it in the existing CI, edit it by hand in VS Code. The gate governs edits the *agent* makes while attestqa is running; a human editing a file is never blocked.

What attestqa adds is beside the code, never inside it: the ledger under `.aqa/`, the policy file, and a provenance comment at the top of each generated spec naming the run, the story, and who approved it. Delete `.aqa/` and the comment and the suite is indistinguishable from a hand-written one.

Two decisions follow from this (both agreed):

- **The tracker is optional.** ADO and Jira are inputs for Specify and sinks for Attest's bug records, and nothing more. With no tracker, a story is a pasted paragraph and a bug is a Markdown file under `.aqa/bugs/`. The runtime already treats work-item field edits as a capability it does not have; the product keeps it that way.
- **The ledger is disk-only.** No attestqa server ever receives a ledger. A team that wants to aggregate can commit `.aqa/` or ship it with their own tooling. The ledger is the user's evidence, and evidence that leaves the machine stops being theirs.

## 3. Bring your own model

The runtime has `agent.model.provider` (`src/runtime/provider.ts`, `src/runtime/openai.ts`): one adapter contract, a credential read from the environment, never from config. The desktop app puts a UI on that seam and adds the authentication modes a company laptop actually has.

| Provider | Wire format | Auth mode(s) | Where the credential lives on Windows |
|---|---|---|---|
| Anthropic | Messages API | API key | Windows Credential Manager, entry `attestqa/anthropic` |
| OpenAI | chat/completions | API key | Credential Manager |
| Azure OpenAI | chat/completions, deployment in path | API key **or** Entra ID (`DefaultAzureCredential`: the user's signed-in Windows account, device-code sign-in, or a managed identity on a build box) | Key in Credential Manager; Entra tokens cached by MSAL, refreshed silently |
| AWS Bedrock | Converse API (Anthropic, Llama, Mistral models behind one shape) | AWS SSO / Identity Center profile, or access keys | `~/.aws/config` profile; the app runs `aws sso login` when the token has expired |
| OpenAI-compatible gateway | chat/completions | Whatever the gateway wants (bearer, mTLS, header) | Credential Manager; the gateway is how a company puts its proxy, logging and spend limits in front of any model |
| Local | chat/completions (Ollama, vLLM, LM Studio) | none | — |

**Why no "Copilot" row.** A desktop app cannot borrow a Copilot seat; GitHub's model endpoints are licensed to GitHub's own clients. A company standardised on Copilot almost always has an Azure tenant, which is the Azure OpenAI row with Entra sign-in — the same identity the user already has on the laptop.

**Adapter conformance.** Every provider must pass the same contract test (`test/provider.test.ts` is the seed): tool calls come back under the runtime's qualified names, malformed arguments become an empty argument set (so the gate refuses the call rather than the run dying), a provider error surfaces as an error and never as an empty decision, usage is recorded, and no provider-side conversation state is kept — every cycle is rebuilt from the ledger. A provider that keeps its own memory would make the ledger a partial record, and the report is counted from the ledger.

**The second-model corpus run** (an open research item) is the same mechanism: change one line in `ai-quality.config.yaml`, run the same 56 stories, compare refusal counts.

## 4. The four rules the app never breaks

These come from the runtime and the corpus, not from the product discussion; the product just promises not to lose them.

1. **A test may be strengthened; it may not be softened.** `writeOnExecutePath`, `weakensAQuarantinedTest`, `editorialOnly`, `swallowedFailure`: a write on the execute path that removes an assertion, or a line that is neither a locator nor a catch, is refused with the reason. Red stays red until a human rules.
2. **The report is counted, never narrated.** Passed, failed, quarantined, refused, denied are tallied from `events.jsonl`. The model's closing note is shown, labelled as the model's note, and never used as a result.
3. **Capability removal beats instruction.** The agent has no tool that edits a work-item field, no `--llm-skip-governance`, no read of a credential file. What it must not do, it cannot do.
4. **Every refusal is closeable by the agent it is told to.** A refusal names what would satisfy it (read the file first; run the whole suite; cite an observation). A refusal that only a human can clear is a stall, and stalls are bugs in the runtime.

## 5. Desktop architecture

**Shell: Electron.** Cypress shipped a desktop test runner in Electron for years; Playwright's own trace viewer and codegen are Electron/Chromium. Node is the runtime the governed loop already runs in, so the main process hosts it unchanged.

**Three processes, not one.**

| Process | Holds | Why separate |
|---|---|---|
| Renderer (UI) | Review views, policy display, the question box | Must never see a credential or the raw model request |
| Main | Credential Manager access, provider build, the ledger writer, IPC | The one trusted process; the only one that reads `.env`-equivalent secrets |
| Worker (utility process) | The governed loop and Playwright | A 40-minute run must not freeze the window; a crash in Playwright must not take the ledger writer with it |

**Browser pane.** v1 runs Playwright headed in its own Chromium window beside the app — zero integration risk, and the user sees exactly what the test sees. v2 embeds the page in an Electron `WebContentsView` driven over CDP, so Explore mode can highlight the element the agent is describing. v1 ships first; v2 is a feature, not a prerequisite.

**Code signing.** An unsigned Windows installer gets a SmartScreen wall and most corporate laptops refuse it. Budget for an OV certificate (Azure Trusted Signing is the cheap route for an open-source project) and a signed auto-updater. This is a release-blocking item, not a polish item.

**Install footprint.** The app bundles Node and Playwright's browsers. First run offers to create or open a project folder and installs `@playwright/test` into it so the suite runs without the app.

## 6. The UI is review, not chat

A chat window is the wrong primitive: it invites the user to argue a test into passing, which is the exact behaviour the runtime exists to prevent. The app has no free-text prompt that reaches the model.

**Always visible:** the policy strip — mode, provider, scope (which URLs, which folder), and the count of refusals and pending approvals in this run.

**Explore view:** the site map as the agent built it, each page with observed behaviours and open questions. Actions: *promote to feature*, *mark out of scope*, *ask the agent to look again at X* (a bounded re-explore, logged as a call).

**Specify view:** story on the left, derived scenarios on the right, each scenario linked to the AC it covers and the generated spec lines. Actions: *approve*, *edit scenario text* (regenerates the spec through bdd2pw; the edit is a ledger event with the user as author), *reject with reason*.

**Attest view:** the counted report. Each failure shows the assertion, the observation, the triage verdict and its evidence, and the agent's proposed action — which the user approves or denies. A quarantined test shows what the agent was refused when it tried to touch it. Actions: *confirm as defect* (files the bug, with the ledger excerpt as the reproduction), *rule not a defect* (becomes a citable ruling, as the AB#44 PO comment did), *leave open*.

**The question box.** The one place the user types. It is answered from the ledger, not by the model: "why is test 7 quarantined?", "what did the agent try to change?", "which runs touched login?" are queries over `events.jsonl`. If a question needs the model, the answer says so and offers to make it a bounded call.

**First run:** choose a folder → choose a provider and sign in (Entra or AWS SSO where available, else paste a key into Credential Manager via the app) → open a URL → the app offers Explore. Five minutes to a first feature file.

---

## 7. Open source first, web later

**Why desktop first.** Credentials stay on the laptop; the browser under test can reach intranet sites and VPN-only environments; the ledger is disk-only by construction; there is nothing to host and no account to create. Every one of those is a reason an enterprise security review says yes.

**License.** MIT, as the runtime is. The provider adapters, the gate rules and the ledger format are the parts worth keeping open: they are what a reviewer has to be able to read to trust the report.

**The web version** comes after, and reuses the worker: the same governed loop behind an MCP server (docs/RESEARCH_mcp_2026-10-07.md — `run_story` returns a handle, `run_status` polls, resources at `aqa://runs/<id>`, no `approve()` tool, config server-side). The web UI is the same three review views over the same ledger. The difference is who holds the credential and where the browser runs, which is exactly the part a company will want to decide for itself.

## 8. Build order

| # | Item | Depends on | Done when |
|---|---|---|---|
| 1 | Publish `attestqa` 1.1.0; publish the `@vijaypjavvadi/agentic-qa` shim; deprecate the old name | `npm test`, `npm run build` on Windows | `npx aqa --version` works from both names |
| 2 | Bedrock provider (Converse API) + conformance test | 1 | `test/provider.test.ts` passes with a fourth row |
| 3 | Entra and AWS SSO auth modes in `provider.ts` (token sources, not keys) | 2 | A run against Azure OpenAI with no `AZURE_OPENAI_API_KEY` set |
| 4 | Electron shell: main + worker + headed Playwright; Attest view only | 1 | A frozen-corpus story runs end to end from the app and the ledger matches the CLI's |
| 5 | Credential Manager integration; first-run flow | 3, 4 | No secret in any file the app writes |
| 6 | Specify view (story → bdd2pw → approve) | 4 | AB#44 reproduced from the UI |
| 7 | Explore mode: new skill, oracle-less, `.feature` drafts only | 6 | Juice Shop explored to a site map without a story |
| 8 | Signed installer + auto-update | 4 | Installs on a SmartScreen-default laptop without a warning |
| 9 | Report completeness (unconditional triage verdicts; `@bug:<id>` tags) | — | Already-filed line appears whether or not `duplicateBug` fired |
| 10 | Second-model corpus run | 2 or 3 | Refusal counts for two providers on the same 56 stories |
| 11 | Browser pane v2 (embedded, CDP) | 7 | Explore highlights the element it is describing |
| 12 | MCP server subcommand → web version | 4, 9 | Same ledger from a browser-hosted UI |

Items 1–3 are runtime work and can be done before any Electron code exists. Item 4 is the first thing a user can install. Items 9 and 10 are the research thread and run in parallel.
