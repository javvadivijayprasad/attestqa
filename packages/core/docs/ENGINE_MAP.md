# attestqa engine map

**Status:** working reference, started 2026-10-18 after a day of run-by-run fixes on Toolshop.
**Rule for every change to the engine:** read the relevant section here first, follow the [fix protocol](#10-fix-protocol), and update this file in the same change.

---

## 1. Why this file exists

On 18 Oct, seven Toolshop runs each stopped on a different problem. Each fix was real, and each one uncovered the next. The pattern came from fixing symptoms one rule at a time, without a picture of how the parts interact. This file is that picture.

## 2. The pipeline: stages and who owns each

| # | Stage | What happens | Owned by (code) |
|---|---|---|---|
| 0 | Route | Decide A (new tests), A2 (complete missing items), or B (run existing tests) | `route/route.ts`, `skills/story-to-tests.ts` (`reroute`) |
| 1 | Story context | The runtime reads the story, epic, siblings, comments, open bugs and framework *before* the model's first turn | `skills/story-context.ts`, `skills/jira-story-context.ts`, `framework/survey.ts` |
| 2 | Test design | The agent proposes items (`aqa.test_design`); the runtime checks them; a person approves. With `SYNTHDATA_CLI` set, the agent may first call `synthdata.examples` for a form field's boundary and invalid values and put them in the item's conditions (2.3.0). For a number range a criterion states, that call is required: `rangeValuesOwed` sends the design back until the tool has been asked for the range. The tool writes only its own output directory, and `designFirst` names the calls it refuses | `design/test-design.ts` (`validateDesign`), `design/stated-ranges.ts` (`rangeValuesOwed`), `skills/story-rules.ts` (`invalidDesign`, `takenDesignIds`, `designFirst`), `mcp/adapters/synthdata.ts` |
| 3 | Authoring | The agent writes the epic's `.feature` scenarios from the approved design. Generated values go in as one Scenario Outline with an inline Examples table, an ordinary feature write under the same rules; bdd2pw's `--data` is not used because it replaces the Examples of every outline in the shared epic file | the agent, policed by the feature rules (§6) |
| 4 | Build | `bdd2pw.analyze`, then `bdd2pw.scaffold`, generate the spec and page object | `mcp/adapters/bdd2pw.ts` and the bdd2pw package |
| 5 | Implement | The agent fills in the TODO steps bdd2pw could not bind | the agent, policed by the spec rules (§6) |
| 6 | Execution | `pw.run_tests` (first run needs approval; the runtime may also run it itself via `autoRun`) | `mcp/adapters/pw.ts`, `runtime/loop.ts` |
| 7 | Triage | Each failure is classified (product defect, flaky, test problem, environment); possible defects are **quarantined** | `triage/classify.ts`, `triage/patterns.ts`, `triage/step.ts` |
| 8 | Heal | A locator failure switches the agent to the `heal` role | `agents/roles.ts`, `mcp/adapters/heal.ts`, `heal/locator.ts`, `heal/second-opinion.ts` |
| 9 | Defects | Bug proposals are held to the end, settled against the final run, then put to a person | `runtime/loop.ts` (`settleDeferredBugs`), `triage/settle.ts` |
| 10 | Verify | Gaps between what was asked and what exists; one retry, then blocked | `verify/story-to-tests.ts`, `triage/step.ts` |
| 11 | Report | `jira.record_qa` / ADO comment; stage lines and totals in the terminal | `report/qa-record.ts`, `runtime/stages.ts` |

## 3. Agents (roles)

There is **one model**. A *role* narrows the tools and instructions it sees. Code chooses the role from the ledger; the model never chooses it.

| Role | When | Tools | Instructions |
|---|---|---|---|
| `default` | Everything except healing | All of the skill's tools | The full story-to-tests instructions (about 9,200 tokens) |
| `heal` | The last suite run has a failure where `stuckAction(message)` is true, or a test that catches its own failure | `aqa.heal_locator`, `fs.read_file`, `fs.replace_in_file`, `pw.run_tests`, `pw.list_tests` | `HEAL_INSTRUCTIONS` in `agents/roles.ts` (about 25 lines) |

**Known defect (F1):** `stuckAction` relies on `LOCATOR_ERROR`, which matches `waiting for getBy…`. Playwright writes that line in the call log of **every** `expect(locator)` failure, including plain assertion mismatches that have a `Received:` line. So assertion failures are sent to the heal agent as "a locator that matched nothing" (Toolshop AC-3, `toHaveAttribute` with `Received: "page-link"`).

**Fixed 19 Oct:** `valueMismatch()` in `heal/locator.ts` is now checked first. A `Received…:`, `Expected pattern|…:`, "unexpected value" or `expect(received).toX(expected)` failure is an assertion, unless the element was not found. `stuckAction()` (used by the heal role, `aqa.heal_locator` and the bug rule `unhealedLocator`) returns false for it. Replaying run `223256Z`: the heal role that was started at event 116 no longer starts. Tests: `test/classify-failures.test.ts`.

**Heal is scoped to the run's own story (W28/W19, fixed in 2.1.0, F-0126/F-0101):** `roleFor(events, storyId)` takes the run's story (`skill.workItem`), and `healableFailure` skips a failing test that belongs to ANOTHER story in a shared epic file — a leftover the run did not write, matched by the `@story` tag on its scenario in the feature file (`otherStoryScenarios`, the signal that survives a scaffold the run has not read) or by the `@story` comment in the spec (`otherStoryTestTitles`). Such a test goes in the report, not the repair queue. An untagged test is nobody's and stays in scope; no story id leaves the behaviour unchanged. Replaying the real SCRUM-25 run: heal moved from SCRUM-24's "Create Address" scan to SCRUM-25's own test. Tests: `test/w28-heal-own-story.test.ts`. Not yet done: scaffold still generates another story's scenarios (the generation half of W28).

**The heal role ends when the healer says the control is not there (2.3.0):** the role used to last as long as the failure did. Runs `20261114T144930Z` and `20261114T145555Z` (TOOL-34, route B): the test for a 75-year-old waits for a refusal message the application never shows; `aqa.heal_locator` answered "the control may genuinely be absent - say so in the bug"; the run stayed in the heal role, which has no bug tool, and ended blocked with a real defect unreported. `aqa.heal_locator` now returns `controlOnPage`, and `healableFailure` skips a failure for which a heal call in this run answered `controlOnPage: false` (older ledgers: the verdict's wording), for as long as the test still fails on the selector that call was asked about. Tying it to "since the last run" lasted one turn: in `20261114T151820Z` the default role scoped another test's scan, the suite ran again, and the run was back in the heal role for the same failure. A failure on a different selector starts the role again. In the same change the `suite-not-green` gap names the run's failing tests that have no bug (not those already reported, already filed, exhausted or held as candidates) and says the two things that can be done: correct the test, or propose a bug. Once the run could propose, it proposed TOOL-36's defect again under another title (`20261114T152437Z`): `duplicateBug` -> `sameFailingTest` looked for the open bug by the test's name in its text, which a Jira search does not return. `openBugAbout` now takes the failing tests and, for a bug the tracker links to the story, reads its title the way a proposal's is read; the verifier and `duplicateBug` both go through it. Tests: `test/unrepairable-failure.test.ts`.

**A changed item's test is not healed (2.3.0):** `healableFailure` skips a failing test named in the last route's `because.changed`. Its expectation was replaced by the design approved in this run, so a text that is no longer on the page is out of date, not a locator that moved; the default role rewrites it with the design in view. Run `20261113T014353Z` sent four such tests to the heal role, each got a list of unrelated locators, and none was changed. A changed item's test that later loses a real locator is repaired by the default role, which has `aqa.heal_locator` too. Tests: `test/changed-design-items.test.ts`.

## 4. Context the model sees each cycle

`runtime/context.ts`, `OrderedContextBuilder`. Each cycle sends the following sections; only their hashes and token counts go into the ledger:

| Section | Content | Size seen |
|---|---|---|
| `instructions` | The skill's instructions, plus the role's. Since 19 Oct, step 4 says every assertion states only what the design item expects, where a state sits is read from the snapshot, and `getByTestId` is preferred when the framework profile names a `testIdAttribute` (now read by `framework/survey.ts`) | about 9,200 tokens (`default`) |
| `request` | "Write tests for TOOL-6" | tiny |
| `tool_schemas` | The schemas of the visible tools | about 4,200 tokens |
| `sources` | Story context and source reads, up to 16,000 characters each (`SOURCE_CHARS`); with document search on, each `docs.search` result | about 6,000 tokens |
| `history` | One compacted line per earlier call (2,000 characters each, `STEP_CHARS`); identical items are de-duplicated; the oldest are kept first up to a cap | grows to about 8,000+ tokens |
| `notes` | Refusals, gaps and runtime notes | small |

Each cycle is about 25–30k input tokens. A 1.5M-token budget is therefore only about 50–60 cycles, so every wasted cycle matters.

## 5. Loop controls (`runtime/loop.ts`)

| Control | What it does |
|---|---|
| Budgets | `budgets.steps` and `budgets.tokens` from the config (eval: 150 steps, 1.5M tokens) |
| `MAX_STALE_CYCLES = 3` | A cycle whose calls were all made before counts as stale; three in a row means blocked. On each stale cycle the repeat is fed back, not executed; a repeated `*.read_file` gets a read-specific nudge — it has the file, so the next call must change something or end the run (W24, F-0109/F-0111/F-0124) |
| `refusedAt` | A refused call is a repeat only while nothing has succeeded since (18 Oct fix) |
| `MAX_SAME_REFUSAL = 5` | The same tool refused for the same reason five times means blocked (18 Oct) |
| `MAX_SAME_DESIGN_PROBLEM = 6` | The same design problem six times means blocked |
| `MAX_DESIGN_DENIALS = 2` | A denied design goes back to the agent with the reviewer's reason, twice; the third denial ends the run. The reason comes from the terminal prompt or, from 2.3.0, from an optional `reason` in the approval file (`runtime/approvers.ts`, `readDecision`). Before that the file's reason was dropped: run `20261112T223242Z` was denied three times with a written reason and the agent submitted the same design each time |
| `deferredBugs` | Bug proposals are refused as "deferred" and settled at the end |
| Mixed-bug rule | A bug in the same approval batch as other calls is refused |
| `approve_execution` | The first suite run needs a person's approval |
| `autoRun` | The runtime runs the suite itself when the spec changed since the last full run. Also once more, unchanged, after the suite's FIRST failing report (`retryOwed` in `runtime/rerun.ts`): the loop asks `autoRun` up to twice before a model turn, so the model's first look at a failure is at one that came back. Held before the FIRST run while the run is bringing changed items' tests into line (see `reroute`): until the agent writes to the feature, spec or page object, or has had `TURNS_TO_UPDATE_CHANGED` = 6 turns without writing (`waitingForChangedTests`). The agent may still run the suite itself **First run, since 2.4.0:** it waits while approved design items have no test on disk (`waitingForNewTests`: no scenario of the story tagged for the item, or a scenario with no test in the spec), until they have, or the agent ends a turn with no call (it says it has finished: a `verify` event after the design). Beside it, unchanged, the wait for tests of CHANGED items (`waitingForChangedTests`). |
| `reroute` | B → A2 when an approved design adds items, or (2.3.0) changes items that already have a test: `because.changed` lists them (`design/cases.ts` `changedItems`, against `because.previousDesign` on the first route), their scenarios are left out of `because.locked`, and the authoring tools stay withheld when nothing is added. Decided once, at the switch |
| Verifier retry | One retry with the gaps fed back, then blocked |

## 6. Refusal rules: 36 in `makeStoryRefusal`, plus 4 for the design

Grouped by stage, in the order the chain checks them (first match wins).

**Records (trackers):** `duplicateTestCase`, `duplicateBug`, `agentRunReport`, `untaggedTestCase`, `wrongSuiteTarget`

**Order of work:** `specBeforeScaffold`, `featureFirst`, `unboundStepsBeforeScaffold` (relaxed 18 Oct: after a second analysis), `scaffoldWouldOverwrite`, `noFramework`, `frameworkOwned`, `notInstalled`, `scratchInTheSuite`, `wrongEpicFile`

**Shared epic feature file:** `rewordsAnotherStory`, `dropsAnotherStory`, `untaggedScenario`, `missingKindTags`, `appendOnlyAfterReroute`, `appendOnlySpec`, `writeOnExecutePath`

- **The document index is outside the pipeline (2.4.0, first slice of ADR-008).** `aqa index` (`knowledge/build.ts`) reads the folders in `agent.knowledge.paths`, cuts Markdown and plain text into passages at their headings (`knowledge/passages.ts`; a passage id is `<file>#<heading slug>@<8 hex of its content hash>`) and writes `passages.jsonl`, `keywords.json` (BM25, `knowledge/bm25.ts`) and `manifest.json` under `<ledger>/knowledge/`. It is a command a person runs: no stage owns it, no rule or loop control acts on it, and a run reads the index only through `docs.search` (next entry); the citation check is the slice after. What is fixed now, because later slices and every recorded citation depend on it: where a document is cut and how a passage is named (`CHUNKER_VERSION`), the tokeniser and the query's stop words (`TOKENISER_VERSION`), and what is never indexed — the ledger, `.aqa-report`, `.aqa-profile`, `test-results`, `playwright-report`, `node_modules`, credential files by name, and any file `isRunReport` recognises. That last list is the provenance rule of §9 applied to documents: the agent must not be able to search its own output. The index is never rebuilt by a run; `staleness` reports the difference for the search tool to show. Test: `knowledge-index`.
- **`aqa eval` is outside the pipeline and changes no run (2.4.0, fourth slice of ADR-008).** `report/eval*.ts`, beside `report/coverage.ts`. It reads ledgers, the document index and a gold file, and writes `eval.json`; no stage owns it and no rule or loop control acts on it. Two levels: the gold file's questions put to `searchKeywords` exactly as `docs.search` runs them (hit rate at 5, mean reciprocal rank, what comes back for unanswerable questions), and recorded runs measured from their events (`runMetrics`): completion from the `end` event, value correctness and invented values from the approved `aqa.test_design` call against the gold values and against everything a tool returned before it (a gold value is looked for in the whole item, its quote included; what counts as wrong or invented is `assertedValues` — numbers in conditions and expected results, quoted wording in expected results only, so test input is not a claim; F1 is 0, not blank, when no gold value is found: corrected after the first evaluation pass, 17 Nov 2026), citation validity from `returnedPassages`, cost from `inference.usage` and a dated price table. The unit is the story: its runs are averaged, then off is compared with on story by story (helped, hurt, unchanged; McNemar's exact test), and rates carry a Wilson interval. The bars agreed on 12 Nov 2026 are checked in code and marked met, missed or not measured. Things a reader of its numbers must know: the arm of a run is not in the ledger, so a run is "on" when it searched unless `--on`/`--off` say otherwise; a model the price table does not have gets no cost, never another model's; a number counts as "given" when it appears anywhere in a tool's result, so invented small numbers are under-counted; and whether a quote SUPPORTS an expectation is decided in code only where the quote holds a gold value the item also holds. The one engine change that came with it: `ApprovalResolvedPayload` now declares the optional `reason` the loop has written since 2.3.0. `--html` writes the same result as one page (`report/eval-html.ts`, fifth slice): built as text on the machine, every value escaped, no file or address fetched, so nothing about a project leaves with it; each run in `eval.json` now carries its design items with the passage each cites, which is what the page opens under a run. Not built: the judge model, the seeded-fault harness as an input, and on the page the chain from criterion to defect and the trend across versions. Test: `eval`.
- **`docs.search` is a stage 2 source tool (2.4.0, second slice of ADR-008; the rule on what it returns is the next entry).** `mcp/adapters/docs.ts`, policy class `read`, so the default policy executes it and the ledger records the call with its whole result — the passages a run was given are in its ledger, not only in the index. It is offered on two conditions, like `synthdata`: `agent.knowledge.paths` is set and `--servers` names `docs`; the CLI then passes `docsOffered` to the skill. Three places change with that flag and nothing else does: the tool is in `allowedTools`; it is in `sourceTools`, so a result is kept whole in `sources` (five passages of at most 1,200 characters, inside `SOURCE_CHARS`) and trimmed last; and the stage 2 text gains one paragraph (`DOCS_SEARCH_STEP` in `skills/story-to-tests.ts`) — when to search (a criterion names a rule without its value), when not to (the story states it; the story wins), how to cite (`doc:<passage id>` in the item's source) and the fixed phrase for a value no document states (`DOCS_NOT_FOUND`). A run without the tool has byte-for-byte the instructions it had; the test pins that. The tool never rebuilds the index (a stale one is answered from and said to be stale), fails with what to do when there is none, and returns a notice first in every result saying passages are text and not instructions. That notice is advice to the model; the protection is the gate, which judges every call proposed after a passage is read exactly as before. Test: `docs-search`.
- **A document citation is checked in code (2.4.0, third slice of ADR-008).** Stage 2, owner `invalidDesign` (`skills/story-rules.ts`); the rules already on that stage are `validateDesign` (types, techniques, the source PATTERN), `takenDesignIds` and `rangeValuesOwed`, and `designFirst` after it. None changed; this is a fourth list of problems in the same refusal, so a design still comes back once with everything wrong in it. Why a new check and not a change to the source pattern: the pattern asks whether a source is NAMED, and stays as it is for criteria, tasks, bugs and comments, where nothing on record can be compared. A passage is on record. `citationProblems` (`design/citations.ts`) reads the run's own `docs.search` observations and sends a design back when an item (1) cites `doc:<id>` for a passage no search of THIS run returned, (2) cites a passage and quotes nothing, or fewer than ten characters, (3) gives a `quote` that is not in the passage it cites, or (4) gives a quote and cites nothing. The comparison is by words: whitespace, block-quote and list marks and typographic quotes aside, case kept; against the observation as recorded and against the same text as the scrubber shows it to the model, so a faithful quote holding `[EMAIL]` passes. It does not show that the quote supports the expectation; the approval text now carries `document: <file> › <heading> says "<quote>"` under the item's `expect:` line so a person can judge that. The design item gains an optional `quote` (tool schema, `parseDesign`); the stage 2 text about it is inside `DOCS_SEARCH_STEP`, so it is in no run that lacks the tool. **A carried design** (stage 0, `route` in `skills/story-to-tests.ts`): before an unchanged story's design is reused, `citationsNotIn` looks its cited passages up in the index as it is now (`knowledgePassages`, read by the CLI). A passage id ends in a hash of its text, so one that is gone means the document changed or was removed; the story is then designed again, with `because.citedPassagesGone`, and so it is when there is no index to confirm against. The story fingerprint is untouched, so no existing story is sent back to design by this release. A design that cites no document is reused exactly as before. Replayed: `20261116T150143Z` (Booker #92) cited three passages, all returned in that run, and quoted none — today's rule sends that design back three times over, and passes it once each item quotes its passage. Test: `design-citations`.
- **Follow-ups from the first live runs with document search (16 Nov 2026, Booker #92; the first is fixed in 2.4.0, see next entry).** (1) *The suite is run before the story has a test.* `autoRun` (`skills/story-to-tests.ts`) returns "nothing has run yet" as soon as a design is approved and the epic's spec exists. On route A2 with no scenario of the story yet, that runs the other stories' tests first. In `20261116T145534Z` the agent then took story 176's contact-form tests for its own and reported done; the verifier ended the run blocked on `design-item-not-tested`. The same early run is in `20261112T224735Z`, `20261112T225751Z`, `20261113T232806Z`, `20261114T141230Z` and `20261115T001654Z`. Stage 6, owner `autoRun`; the hold that already exists for changed tests (`waitingForChangedTests`) is the place to look. (2) *A search never says "nothing found".* BM25 returns every passage that shares a word with the query, so a search for a value no document states came back with four passages and the agent did not use the `DOCS_NOT_FOUND` phrase in either run. The skill text now asks for the phrase in the item's conditions (the agent never filled `rationale`); that wording has not been tried live. Whether the tool should apply a floor to the score is a question for the retrieval evaluation. (3) *One wrong test, correctly not filed.* In `20261116T150143Z` the test for "a message for each required field" read the input's `validationMessage`; the application answers with a list on the page ("Name may not be blank", …). The bug proposed for it was denied by the reviewer. The required-field messages were not in the project document, which is the case finding (2) is about.
- **The suite's first run waits for the story's own tests (fixed in 2.4.0).** Stage 6, owner `autoRun` (`skills/story-to-tests.ts`); the other controls on that stage are the first-run approval (`approve_execution`), `staleRerun` and `retryOwed` (`runtime/rerun.ts`), and the wait for changed tests — none of them changed. `autoRun` returned "nothing has run yet" as soon as a design was approved and the epic's spec existed. On a new feature file that is after the scaffold, when the story's tests exist. In a file other stories share (route A2, or B→A2 with new items) it was at once: a run of the neighbours' tests, and a second one when any of them failed. In `20261116T145534Z` both runs happened before the agent's first turn after the design; it saw a finished suite holding story 176's contact-form tests, reported story 92 done without a write, and the run ended blocked on `design-item-not-tested`. The measure across 42 recorded runs: on A2 the suite ran at turn 0 after the design while the feature was first written at turns 1 to 7. Changed, not added to: the existing first-run branch now also waits on `waitingForNewTests`, which reads what is missing the way `reroute` does (`coverageOf`), so the two cannot disagree. The wait ends by itself when the agent says it has finished (a `verify` event after the design), so a run that stops short still ends with results for the tests that exist; the model may still ask for a run, under the same rules as before. It is deliberately not a count of turns: a first version waited six turns without a write to the suite, and in `20261116T155959Z` (Booker #93) the agent wrote the feature at its fifth turn, spent the next six exploring the admin pages for the spec, and the runtime asked to run the suite in the middle of that. Route B with every item covered, and every run after the first, are as they were. Test: `autorun` (both real ledgers replayed).
- **`dropsAnotherStory` reads the file on disk when the run has not read it (fixed in 2.3.0).** The rule compared a feature write with what the run's own events knew of the file. Run `20261112T224735Z` (story 176, a model that wrote without reading) overwrote the epic's shared feature file twice and removed story 91's four scenarios; with nothing in the events about the file the rule said nothing. It now falls back to the workspace file, as `rewordsAnotherStory` and `takenDesignIds` already do. With no workspace (a replay of a ledger alone) it behaves as before, so the replay corpus is unchanged; replaying that run with the workspace refuses the first write.

**Two smaller things from the same end-to-end run (2.3.0):**

- **`synthdata.examples` refuses a text-length rule** (`LENGTH(col)` in a `CHECK`). synthdata 1.4.0 ignores it: for a phone of 11 to 21 characters it returned a one-character value as valid. The refusal tells the agent to work the length boundaries out itself; the skill says the same. Number ranges, allowed sets and required fields are unaffected.
- **`synthdata.examples` says which invalid boundary it did not get** (2.3.0). synthdata 1.4.0's `negative` profile breaks a number range only above its maximum: for `age BETWEEN 18 AND 74` it returns 75 and never 17, on every seed (probe of 14 Nov 2026 for TOOL-34's rule). The tool's description had promised "the value one outside a range". The adapter now looks at the rows that came back (`belowMinimumMissing`): for each `BETWEEN` range with no row below the minimum, the answer's `note` and `belowMinimumMissing` name the column and, for whole numbers, the value one below the minimum, and tell the agent to add it. It is quiet once synthdata returns both sides.
- **A design on a stated number range is sent back until the generator has been asked** (2.3.0, `rangeValuesOwed` in `design/stated-ranges.ts`, part of `invalidDesign`). The skill said "call it BEFORE you submit the design" and nothing checked it: in both authoring runs of TOOL-34 (`20261113T232806Z`, `20261114T141230Z`) the tool was offered, the design had three boundary-value items on "A customer aged 18 to 74 can register", and the tool was not called. The rule fires only when all of these hold: `synthdata.examples` is among the run's tools (the CLI asks the tool list, so a run without `SYNTHDATA_CLI` is untouched); an acceptance criterion states a range in words (`18 to 74`, `18–74`, `between 1 and 99`); a boundary-value or equivalence-partitioning item covers that criterion; and no `synthdata.examples` call this run had `BETWEEN low AND high` in its DDL for profile `edge` and for profile `negative`. A range of text LENGTH ("between 11 and 21 characters") is not asked for, because the tool refuses it. A call that ran and failed counts, so a broken generator cannot hold a design back. The rule does not check that the returned values are in the conditions: for an age the form takes a date of birth, and the approver reads both. Replays do not apply it (a ledger does not record which tools were offered).
- **A URL refused for scope names the allowed URLs** (`governance/policy.ts`). Run `20261112T225751Z` took a stale port from a comment in the project, was told only "not in the allowed urls", and tried `127.0.0.1`, `0.0.0.0` and `host.docker.internal` on that port. The refusal now lists `agent.scope.urls` and says another host or port is refused the same way.
- **The run report gives no verdict on a story that has no tests.** When the verifier's last result is that no approved design item has a test, the headline is "No test of story N ran" and the tests that did run are named as other stories'. Before, the report read "Suite: green for story 176 — 4 passed" when all four were story 91's.

- **A changed design item's test is the run's to rewrite (2.3.0).** When the story changed and the design approved in this run gives an existing item (same id) a different expected result, conditions or expect-fail, the test on disk checks the earlier expectation. Run `20261113T014353Z` (AB#176, criteria rewritten to quote the application's messages): `aqa.test_design` answered "every item is already tested … do not rewrite the feature file or the spec", the suite failed on the old wording, the failures went to the heal role, and nothing changed. Now: the first route records the earlier design (`because.previousDesign`); the design tool's result lists `changedItems` (was / now) and says to bring those scenarios and tests into line before the suite runs; the approval note names them; the run switches to A2 with `because.changed`; `appendOnlyAfterReroute` lets those scenarios change (they are not in `locked`) and no longer demands `bdd2pw.analyze` when there is nothing to add; `appendOnlySpec` counts their tests as the run's own, so an `expect` line may be replaced (run `20261113T122522Z` was refused that four times); the heal role skips their failures (§3). Every other scenario and test stays locked as before. ## 7. Triage and quarantine

- **Categories:** `real-defect`, `flake`, `environmental`, `infrastructure`, plus test-code problems, scored by the pattern banks in `triage/patterns.ts`.
- **Test faults (W27, fixed in 2.0.3, F-0125/F-0126):** a `TEST_CODE_ERROR` match (strict-mode violation, invalid selector, axe "No elements found") stays category `flake` — that is what hands the test back to the agent rather than quarantining it — but the verdict now carries an optional `testFault: true`. The category set is ledger contract in 2.0.x, so no new category value was added; the flag is additive and ignorable. The report (`runtime/stages.ts`) counts `testFault` verdicts as "test fault(s)", separately from "flaky", and the verifier's flake note (`triage/step.ts`) excludes them. The rationale is unchanged.
- **Precondition sign-in (W30, fixed in 2.1.0, F-0130):** a failure whose message marks it a precondition and names a login/auth failure, or names the configured credentials (`AQA_APP_USER`/`AQA_APP_PASS`), is decided `environmental` at 0.9 (`PRECONDITION_FAILURE` in `patterns.ts`, checked in `classify.ts` alongside `SETUP_HOOK_FAILURE`). A precondition is setup, so its failure means no step reached the product — the mirror of the test-fault case and the opposite mislabel to W27. A bare 4xx with none of that stays a product failure, as `DECLARED_ENVIRONMENTAL` does. With no test passed the run then reports `environmental` (contagious) and files no defect.
- **`applyRepetition`:** a `flake` that fails the same way twice becomes `real-defect` at 0.1 ("guessing has stopped working"). Since 18 Oct, "the same way" includes the locator.
- **Two different definitions of "quarantined" (F2):**
  - `triage/step.ts` → `quarantines(v)`: `real-defect` **and confidence > 0.1**. The verifier uses this.
  - `skills/story-rules.ts` → `quarantinedTitles()`: **any** `real-defect`, whatever the confidence. The write guard uses this.

  The result: tests the triage step deliberately did *not* quarantine (0.1, "we do not know") are still frozen by the write rule.
- **A brand-new test is quarantined on its first failure (F3):** an assertion mismatch (`Expected pattern:` … `Received`) scores `real-defect` at about 0.4. On a test written minutes earlier and never passed, that is far more likely a test mistake. From then on, `weakensAQuarantinedTest` refuses any change to its expectation.

**Fixed 19 Oct (F2, F3):** there is now one definition, `triage/quarantine.ts`.

- **When a test is quarantined:** only when the verdict is a confident product defect (`quarantines(v)`: `real-defect`, confidence > 0.1) **and** the test is proven. A test is proven if any of these hold:
  - it passed earlier in the run;
  - the run is on the execute path B;
  - it is a scenario locked by a re-route;
  - it is a known-bug test (`test.fail(` or `@bug:`).
- **Who uses it:** triage records the list in `payload.quarantined`. The write guard (`quarantinedTitles`) and the verifier (drift, defect candidates) read that list. Nobody recomputes it.
- **What changed in the notes to the agent:** they no longer say "propose a bug for each red test". Bugs are proposed only for quarantined failures, with the tracker's own tool. A test that has never passed gets a "check the test first" note instead.
- **The terminal:** it now says "new test failing that has never passed — the agent checks the test first; not yet a defect".
- **Replays:**
  - run `223256Z`: AC-3 and the accessibility test are no longer frozen;
  - run `125846Z`: the accessibility test is no longer frozen;
  - AC-2 still gets frozen, because it passed and was then edited. Item 3 (passing tests locked) stops that edit.

The scope rule keeps site-wide header/footer noise off a story, but scoping to a generic page region also drops the story's own controls that sit outside main. The scope guidance (the `shapeProblems` "not scoped" message and the `unscopedAccessibilityBug` refusal in `skills/story-rules.ts`) now says to scope to the story's control wherever it lives, header included, not to `<main>` alone. And `traceProblems` adds a review-only check: an accessibility scan scoped to a generic region only (`GENERIC_REGION`: main/body) when the story is about a control that usually lives in the header or toolbar (`HEADER_CONTROL`: search/menu/cart/nav/…) may have scoped the story's own control out. Across the ledgers it fires on 5 of 113 accessibility items, all the SCRUM-18 search story.
- **A non-functional criterion is covered by its own type (W25, fixed in 2.1.0, F-0112):** `validateDesign`'s coverage rule was "every criterion has a functional test"; AB#110's AC-3 ("the sign-in page passes a WCAG 2.1 A/AA scan") was refused for having no functional item, and the agent added a functional item it implemented as a second copy of the axe scan — coverage padding, which the test-matches-design check did not notice. The rule now accepts a criterion covered by a functional, accessibility **or** security item (`coveringTypes`); confirmation is bug-only and does not count. The design holds only the AC labels, not their text, so the criterion's natural type is read from the item the agent chose, and the reviewer approving the design is the check that the type fits. Scoped across the ledgers: the one real case (AB#110's first design) flips from refused to accepted.
- **Per-test data isolation for stateful stories (W15/W18/W21, fixed in 2.1.0, F-0097/F-0100/F-0104):** SCRUM-19's basket tests shared one account and ran serially, so the product one test added was still in the basket when the next added it — Juice Shop answered 500, a badge expecting "1" read "2" — and the agent repaired locators for nine runs of nine instead of isolating the data. `validateDesign` adds a once-per-story rule (`mutatesSharedState` without `statesIsolation`): a design that changes shared state (a basket, booking or order) must say, in some item or an exclusion reason, how each test gets its own data — a fresh account per test, the state cleared before each test, or a unique datum per test (34 of 113 ledger designs flagged, all e-commerce stateful stories; isolation is a suite-level decision so it is checked once, not per item). `traceProblems` adds a review-only backstop (`bodyMutatesSharedState` without `isolatesTestData` in the body or a shared `beforeEach`): on the real SCRUM-19 spec it flags the AC-1 add that never cleared and leaves the AC-2 test that cleared the basket inline alone. The skill gains guidance that a 500/wrong-count on a stateful setup is a data problem not a locator problem, and (W21) that the page's actual confirmation text must be read from the snapshot, not guessed at with a widened regex. The project's synthetic-data generator (`synthdata.generate`) is offered to the agent as a stage-2 tool — served only when `SYNTHDATA_CMD` is set, so a no-op otherwise — and `statesIsolation`/`isolatesTestData` recognise it as the unique-datum isolation strategy, so a design or spec that generates a unique datum per test with it passes the gate. Whether the agent then isolates well enough to finish a stateful story within budget is a model question, measured in a run.
- **An accessibility violation survives a never-passed test (W21, fixed in 2.1.0, F-0104):** the bug gate withholds a defect from a test that never passed, because a never-passing functional test may itself be wrong. But an axe scan reports facts about the DOM, so a rule it flags is real whether or not the test passed — SCRUM-21's `button-name` on an icon-only button recurred across runs and was never surfaced. The verifier's green-suite check now reads each failing test's message through `axeRuleIds` (an axe scan that found concrete rule ids, not one that threw or was empty — triage handles those): such a failure is put to the reviewer and counted toward `allDefects`, so the run ends with the violation reported rather than only "suite not green". Review-only — a scan can be mis-scoped (W11), so it is surfaced for a person, not auto-filed. Confirmed by replaying the SCRUM-21 ledger: the `button-name` violation surfaces, and SCRUM-18's `color-contrast` (another story's) does not.
- **The fixture account is left usable (W33, fixed in 2.1.0, F-0151/F-0130):** SCRUM-10's forgot-password test reset the shared account's password and never put it back, so a whole-suite parallel run answered 401 on every sign-in after it; nothing in the design rules, verifier or triage looked for it. A design rule (`validateDesign`) now requires an item whose *expected result* changes an account credential (`mutatesAccount`) to state the restore (`leavesFixtureRestored` — restore the original, or use an account the test creates); scoped to the expected result, not the conditions, so a sign-in entering a password and an axe test signing in before scanning are not caught (6 of 557 ledger items flagged, all genuine). A refused/rejected/"not changed"/requires-authentication case does not mutate and is excluded. The verifier backstop (`traceProblems`, review-only) reports a test whose body runs the change flow (`bodyMutatesAccount`) when nothing in the whole spec — an `afterEach`/`afterAll` hook included — restores it.
- **Every item has a test, and a negative assertion names an element (W8/W10, fixed in 2.1.0, F-0090/F-0092):** `design-item-not-tested` used to read the feature file alone, so an item whose scenario was tagged but whose spec test was dropped or never written read as covered. `traceProblems` now also requires a spec body referencing each `@design:<id>` once a spec exists (with no spec on disk, `no-spec-written` still carries it). And `proseAbsenceAssertion` (a review-only `shapeProblems` check) flags a negative/absence assertion — `.not.toBeVisible()`, `.toBeHidden()`, `.toHaveCount(0)` — located by TEXT (`getByText`, `text=`, `:has-text`): "no product cards" asserted as `getByText("product cards").not.toBeVisible()` passes whenever that phrase is simply unprinted, whatever the product does. The semantic weaknesses the findings also name (absence never checked, an assertion a product name satisfies) are the paper's measurement, not a mechanical rule, and stay with the reviewer.

**The three structural causes:**

- **C1, guessing.** The agent writes expectations from assumptions, not from the page or the design. Examples: the URL changes to `?page=2`, `active` sits on the button, titles are present immediately. It also "repairs" tests that are passing.
- **C2, quarantine too early.** A brand-new, never-passed test is frozen as a defect candidate on its first failures. This blocks the only repair that could fix it, made worse by F2.
- **C3, rules piled up.** 36+ rules, each correct alone, collide in practice. There's no test of how they interact.

## 10. Fix protocol: follow it for every engine change

1. **Locate the stage and owner** in §2, and read that code.
2. **List every rule and loop control** (§5, §6, §7) that acts on that stage, and read each doc comment.
3. **Prefer changing or removing a rule over adding one.** A new rule needs a stated reason why no existing rule could carry it.
4. **Replay the real ledgers** that showed the problem against the change (they live in `packages/core/.aqa/runs/` and `TestRunApplication/*/.aqa/runs/`). Write a test from the real events.
5. **Check interactions:** run the rule-interaction tests (to be added, §11 step 4).
6. **Update this file** (§3–§9) in the same change.
