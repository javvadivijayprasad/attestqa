# attestqa engine map

**Status:** working reference, started 2026-10-18 after a day of run-by-run fixes on Toolshop.
**Rule for every change to the engine:** read the relevant section here first, follow the [fix protocol](#10-fix-protocol), and update this file in the same change.

---

## 1. Why this file exists

On 18 Oct, seven Toolshop runs each stopped on a different problem. Each fix was real, and each one uncovered the next. The pattern came from fixing symptoms one rule at a time, without a picture of how the parts interact. This file is that picture.

## 2. The pipeline: stages and who owns each

| # | Stage | What happens | Owned by (code) |
|---|---|---|---|
| 0 | Route | Decide A (new tests), A2 (complete missing items), or B (run existing tests) | `route/route.ts`, `skills/story-to-tests.ts` (`reroute`) |
| 1 | Story context | The runtime reads the story, epic, siblings, comments, open bugs and framework *before* the model's first turn | `skills/story-context.ts`, `skills/jira-story-context.ts`, `framework/survey.ts` |
| 2 | Test design | The agent proposes items (`aqa.test_design`); the runtime checks them; a person approves. With `SYNTHDATA_CLI` set, the agent may first call `synthdata.examples` for a form field's boundary and invalid values and put them in the item's conditions (2.3.0). No rule acts on that tool: it writes only its own output directory, and `designFirst` names the calls it refuses | `design/test-design.ts` (`validateDesign`), `skills/story-rules.ts` (`invalidDesign`, `takenDesignIds`, `designFirst`), `mcp/adapters/synthdata.ts` |
| 3 | Authoring | The agent writes the epic's `.feature` scenarios from the approved design. Generated values go in as one Scenario Outline with an inline Examples table, an ordinary feature write under the same rules; bdd2pw's `--data` is not used because it replaces the Examples of every outline in the shared epic file | the agent, policed by the feature rules (§6) |
| 4 | Build | `bdd2pw.analyze`, then `bdd2pw.scaffold`, generate the spec and page object | `mcp/adapters/bdd2pw.ts` and the bdd2pw package |
| 5 | Implement | The agent fills in the TODO steps bdd2pw could not bind | the agent, policed by the spec rules (§6) |
| 6 | Execution | `pw.run_tests` (first run needs approval; the runtime may also run it itself via `autoRun`) | `mcp/adapters/pw.ts`, `runtime/loop.ts` |
| 7 | Triage | Each failure is classified (product defect, flaky, test problem, environment); possible defects are **quarantined** | `triage/classify.ts`, `triage/patterns.ts`, `triage/step.ts` |
| 8 | Heal | A locator failure switches the agent to the `heal` role | `agents/roles.ts`, `mcp/adapters/heal.ts`, `heal/locator.ts`, `heal/second-opinion.ts` |
| 9 | Defects | Bug proposals are held to the end, settled against the final run, then put to a person | `runtime/loop.ts` (`settleDeferredBugs`), `triage/settle.ts` |
| 10 | Verify | Gaps between what was asked and what exists; one retry, then blocked | `verify/story-to-tests.ts`, `triage/step.ts` |
| 11 | Report | `jira.record_qa` / ADO comment; stage lines and totals in the terminal | `report/qa-record.ts`, `runtime/stages.ts` |

## 3. Agents (roles)

There is **one model**. A *role* narrows the tools and instructions it sees. Code chooses the role from the ledger; the model never chooses it.

| Role | When | Tools | Instructions |
|---|---|---|---|
| `default` | Everything except healing | All of the skill's tools | The full story-to-tests instructions (about 9,200 tokens) |
| `heal` | The last suite run has a failure where `stuckAction(message)` is true, or a test that catches its own failure | `aqa.heal_locator`, `fs.read_file`, `fs.replace_in_file`, `pw.run_tests`, `pw.list_tests` | `HEAL_INSTRUCTIONS` in `agents/roles.ts` (about 25 lines) |

**Known defect (F1):** `stuckAction` relies on `LOCATOR_ERROR`, which matches `waiting for getBy…`. Playwright writes that line in the call log of **every** `expect(locator)` failure, including plain assertion mismatches that have a `Received:` line. So assertion failures are sent to the heal agent as "a locator that matched nothing" (Toolshop AC-3, `toHaveAttribute` with `Received: "page-link"`).

**Fixed 19 Oct:** `valueMismatch()` in `heal/locator.ts` is now checked first. A `Received…:`, `Expected pattern|…:`, "unexpected value" or `expect(received).toX(expected)` failure is an assertion, unless the element was not found. `stuckAction()` (used by the heal role, `aqa.heal_locator` and the bug rule `unhealedLocator`) returns false for it. Replaying run `223256Z`: the heal role that was started at event 116 no longer starts. Tests: `test/classify-failures.test.ts`.

**Heal is scoped to the run's own story (W28/W19, fixed in 2.1.0, F-0126/F-0101):** `roleFor(events, storyId)` takes the run's story (`skill.workItem`), and `healableFailure` skips a failing test that belongs to ANOTHER story in a shared epic file — a leftover the run did not write, matched by the `@story` tag on its scenario in the feature file (`otherStoryScenarios`, the signal that survives a scaffold the run has not read) or by the `@story` comment in the spec (`otherStoryTestTitles`). Such a test goes in the report, not the repair queue. An untagged test is nobody's and stays in scope; no story id leaves the behaviour unchanged. Replaying the real SCRUM-25 run: heal moved from SCRUM-24's "Create Address" scan to SCRUM-25's own test. Tests: `test/w28-heal-own-story.test.ts`. Not yet done: scaffold still generates another story's scenarios (the generation half of W28).

**A changed item's test is not healed (2.3.0):** `healableFailure` skips a failing test named in the last route's `because.changed`. Its expectation was replaced by the design approved in this run, so a text that is no longer on the page is out of date, not a locator that moved; the default role rewrites it with the design in view. Run `20261113T014353Z` sent four such tests to the heal role, each got a list of unrelated locators, and none was changed. A changed item's test that later loses a real locator is repaired by the default role, which has `aqa.heal_locator` too. Tests: `test/changed-design-items.test.ts`.

## 4. Context the model sees each cycle

`runtime/context.ts`, `OrderedContextBuilder`. Each cycle sends the following sections; only their hashes and token counts go into the ledger:

| Section | Content | Size seen |
|---|---|---|
| `instructions` | The skill's instructions, plus the role's. Since 19 Oct, step 4 says every assertion states only what the design item expects, where a state sits is read from the snapshot, and `getByTestId` is preferred when the framework profile names a `testIdAttribute` (now read by `framework/survey.ts`) | about 9,200 tokens (`default`) |
| `request` | "Write tests for TOOL-6" | tiny |
| `tool_schemas` | The schemas of the visible tools | about 4,200 tokens |
| `sources` | Story context and source reads, up to 16,000 characters each (`SOURCE_CHARS`) | about 6,000 tokens |
| `history` | One compacted line per earlier call (2,000 characters each, `STEP_CHARS`); identical items are de-duplicated; the oldest are kept first up to a cap | grows to about 8,000+ tokens |
| `notes` | Refusals, gaps and runtime notes | small |

Each cycle is about 25–30k input tokens. A 1.5M-token budget is therefore only about 50–60 cycles, so every wasted cycle matters.

## 5. Loop controls (`runtime/loop.ts`)

| Control | What it does |
|---|---|
| Budgets | `budgets.steps` and `budgets.tokens` from the config (eval: 150 steps, 1.5M tokens) |
| `MAX_STALE_CYCLES = 3` | A cycle whose calls were all made before counts as stale; three in a row means blocked. On each stale cycle the repeat is fed back, not executed; a repeated `*.read_file` gets a read-specific nudge — it has the file, so the next call must change something or end the run (W24, F-0109/F-0111/F-0124) |
| `refusedAt` | A refused call is a repeat only while nothing has succeeded since (18 Oct fix) |
| `MAX_SAME_REFUSAL = 5` | The same tool refused for the same reason five times means blocked (18 Oct) |
| `MAX_SAME_DESIGN_PROBLEM = 6` | The same design problem six times means blocked |
| `MAX_DESIGN_DENIALS = 2` | A denied design goes back to the agent with the reviewer's reason, twice; the third denial ends the run. The reason comes from the terminal prompt or, from 2.3.0, from an optional `reason` in the approval file (`runtime/approvers.ts`, `readDecision`). Before that the file's reason was dropped: run `20261112T223242Z` was denied three times with a written reason and the agent submitted the same design each time |
| `deferredBugs` | Bug proposals are refused as "deferred" and settled at the end |
| Mixed-bug rule | A bug in the same approval batch as other calls is refused |
| `approve_execution` | The first suite run needs a person's approval |
| `autoRun` | The runtime runs the suite itself when the spec changed since the last full run. Also once more, unchanged, after the suite's FIRST failing report (`retryOwed` in `runtime/rerun.ts`): the loop asks `autoRun` up to twice before a model turn, so the model's first look at a failure is at one that came back. Held before the FIRST run while the run is bringing changed items' tests into line (see `reroute`): until the agent writes to the feature, spec or page object, or has had `TURNS_TO_UPDATE_CHANGED` = 6 turns without writing (`waitingForChangedTests`). The agent may still run the suite itself |
| `reroute` | B → A2 when an approved design adds items, or (2.3.0) changes items that already have a test: `because.changed` lists them (`design/cases.ts` `changedItems`, against `because.previousDesign` on the first route), their scenarios are left out of `because.locked`, and the authoring tools stay withheld when nothing is added. Decided once, at the switch |
| Verifier retry | One retry with the gaps fed back, then blocked |

**Design:** `invalidDesign` (+ `takenDesignIds`), `designFirst`

**Design review, not a rule (W2/W6, fixed in 2.1.0, F-0087/F-0088):** on existing-tests stories the design adopts the existing test's scope and labels — a login-page scan on a sign-out story, a security item citing AC-1 while testing AC-3's case — and the source rule, which checks that a source is *named* not that it *supports* the item, passed them, as did the approver. Whether a source supports an item or a page fits the story is a judgement no string match makes. So: each `DesignItem` carries an optional one-line `rationale` justifying its page and source against the story's own text; `renderDesign` shows it to the approver (and says "not justified against the story" when absent — the item most likely copied from an existing test); the design skill asks for it and warns against adopting an existing test's scope; and the design approval (`renderDesignCall`) carries a reviewer checklist — does the source support the item, is the page one the story mentions, is the expected from the story not carried over. No gate; the approver judges.

Each rule was written for a real incident (named in its doc comment). None of them was tested against the others.

## 7. Triage and quarantine

- **Categories:** `real-defect`, `flake`, `environmental`, `infrastructure`, plus test-code problems, scored by the pattern banks in `triage/patterns.ts`.
- **Test faults (W27, fixed in 2.0.3, F-0125/F-0126):** a `TEST_CODE_ERROR` match (strict-mode violation, invalid selector, axe "No elements found") stays category `flake` — that is what hands the test back to the agent rather than quarantining it — but the verdict now carries an optional `testFault: true`. The category set is ledger contract in 2.0.x, so no new category value was added; the flag is additive and ignorable. The report (`runtime/stages.ts`) counts `testFault` verdicts as "test fault(s)", separately from "flaky", and the verifier's flake note (`triage/step.ts`) excludes them. The rationale is unchanged.
- **Precondition sign-in (W30, fixed in 2.1.0, F-0130):** a failure whose message marks it a precondition and names a login/auth failure, or names the configured credentials (`AQA_APP_USER`/`AQA_APP_PASS`), is decided `environmental` at 0.9 (`PRECONDITION_FAILURE` in `patterns.ts`, checked in `classify.ts` alongside `SETUP_HOOK_FAILURE`). A precondition is setup, so its failure means no step reached the product — the mirror of the test-fault case and the opposite mislabel to W27. A bare 4xx with none of that stays a product failure, as `DECLARED_ENVIRONMENTAL` does. With no test passed the run then reports `environmental` (contagious) and files no defect.
- **`applyRepetition`:** a `flake` that fails the same way twice becomes `real-defect` at 0.1 ("guessing has stopped working"). Since 18 Oct, "the same way" includes the locator.
- **Two different definitions of "quarantined" (F2):**
  - `triage/step.ts` → `quarantines(v)`: `real-defect` **and confidence > 0.1**. The verifier uses this.
  - `skills/story-rules.ts` → `quarantinedTitles()`: **any** `real-defect`, whatever the confidence. The write guard uses this.

  The result: tests the triage step deliberately did *not* quarantine (0.1, "we do not know") are still frozen by the write rule.
- **A brand-new test is quarantined on its first failure (F3):** an assertion mismatch (`Expected pattern:` … `Received`) scores `real-defect` at about 0.4. On a test written minutes earlier and never passed, that is far more likely a test mistake. From then on, `weakensAQuarantinedTest` refuses any change to its expectation.

**Fixed 19 Oct (F2, F3):** there is now one definition, `triage/quarantine.ts`.

- **When a test is quarantined:** only when the verdict is a confident product defect (`quarantines(v)`: `real-defect`, confidence > 0.1) **and** the test is proven. A test is proven if any of these hold:
  - it passed earlier in the run;
  - the run is on the execute path B;
  - it is a scenario locked by a re-route;
  - it is a known-bug test (`test.fail(` or `@bug:`).
- **Who uses it:** triage records the list in `payload.quarantined`. The write guard (`quarantinedTitles`) and the verifier (drift, defect candidates) read that list. Nobody recomputes it.
- **What changed in the notes to the agent:** they no longer say "propose a bug for each red test". Bugs are proposed only for quarantined failures, with the tracker's own tool. A test that has never passed gets a "check the test first" note instead.
- **The terminal:** it now says "new test failing that has never passed — the agent checks the test first; not yet a defect".
- **Replays:**
  - run `223256Z`: AC-3 and the accessibility test are no longer frozen;
  - run `125846Z`: the accessibility test is no longer frozen;
  - AC-2 still gets frozen, because it passed and was then edited. Item 3 (passing tests locked) stops that edit.

- **The scan includes the story's own control, header and all (W11, fixed in 2.1.0, F-0093):** SCRUM-18's search box is in the top toolbar; the accessibility scan was scoped to `<main>`, which excludes the toolbar, so a real `label` violation on the search box passed and the run reported nothing. - **A non-functional criterion is covered by its own type (W25, fixed in 2.1.0, F-0112):** `validateDesign`'s coverage rule was "every criterion has a functional test"; AB#110's AC-3 ("the sign-in page passes a WCAG 2.1 A/AA scan") was refused for having no functional item, and the agent added a functional item it implemented as a second copy of the axe scan — coverage padding, which the test-matches-design check did not notice. Scoped across the ledgers: the one real case (AB#110's first design) flips from refused to accepted.
- **Per-test data isolation for stateful stories (W15/W18/W21, fixed in 2.1.0, F-0097/F-0100/F-0104):** SCRUM-19's basket tests shared one account and ran serially, so the product one test added was still in the basket when the next added it — Juice Shop answered 500, a badge expecting "1" read "2" — and the agent repaired locators for nine runs of nine instead of isolating the data. `validateDesign` adds a once-per-story rule (`mutatesSharedState` without `statesIsolation`): a design that changes shared state (a basket, booking or order) must say, in some item or an exclusion reason, how each test gets its own data — a fresh account per test, the state cleared before each test, or a unique datum per test (34 of 113 ledger designs flagged, all e-commerce stateful stories; isolation is a suite-level decision so it is checked once, not per item). `traceProblems` adds a review-only backstop (`bodyMutatesSharedState` without `isolatesTestData` in the body or a shared `beforeEach`): on the real SCRUM-19 spec it flags the AC-1 add that never cleared and leaves the AC-2 test that cleared the basket inline alone. The project's synthetic-data generator (`synthdata.generate`) is offered to the agent as a stage-2 tool — served only when `SYNTHDATA_CMD` is set, so a no-op otherwise — and `statesIsolation`/`isolatesTestData` recognise it as the unique-datum isolation strategy, so a design or spec that generates a unique datum per test with it passes the gate. Whether the agent then isolates well enough to finish a stateful story within budget is a model question, measured in a run.
- **An accessibility violation survives a never-passed test (W21, fixed in 2.1.0, F-0104):** the bug gate withholds a defect from a test that never passed, because a never-passing functional test may itself be wrong. But an axe scan reports facts about the DOM, so a rule it flags is real whether or not the test passed — SCRUM-21's `button-name` on an icon-only button recurred across runs and was never surfaced. The verifier's green-suite check now reads each failing test's message through `axeRuleIds` (an axe scan that found concrete rule ids, not one that threw or was empty — triage handles those): such a failure is put to the reviewer and counted toward `allDefects`, so the run ends with the violation reported rather than only "suite not green". Review-only — a scan can be mis-scoped (W11), so it is surfaced for a person, not auto-filed. Confirmed by replaying the SCRUM-21 ledger: the `button-name` violation surfaces, and SCRUM-18's `color-contrast` (another story's) does not.
- **The fixture account is left usable (W33, fixed in 2.1.0, F-0151/F-0130):** SCRUM-10's forgot-password test reset the shared account's password and never put it back, so a whole-suite parallel run answered 401 on every sign-in after it; nothing in the design rules, verifier or triage looked for it. A design rule (`validateDesign`) now requires an item whose *expected result* changes an account credential (`mutatesAccount`) to state the restore (`leavesFixtureRestored` — restore the original, or use an account the test creates); scoped to the expected result, not the conditions, so a sign-in entering a password and an axe test signing in before scanning are not caught (6 of 557 ledger items flagged, all genuine). A refused/rejected/"not changed"/requires-authentication case does not mutate and is excluded. The verifier backstop (`traceProblems`, review-only) reports a test whose body runs the change flow (`bodyMutatesAccount`) when nothing in the whole spec — an `afterEach`/`afterAll` hook included — restores it.
- **Every item has a test, and a negative assertion names an element (W8/W10, fixed in 2.1.0, F-0090/F-0092):** `design-item-not-tested` used to read the feature file alone, so an item whose scenario was tagged but whose spec test was dropped or never written read as covered. `traceProblems` now also requires a spec body referencing each `@design:<id>` once a spec exists (with no spec on disk, `no-spec-written` still carries it). And `proseAbsenceAssertion` (a review-only `shapeProblems` check) flags a negative/absence assertion — `.not.toBeVisible()`, `.toBeHidden()`, `.toHaveCount(0)` — located by TEXT (`getByText`, `text=`, `:has-text`): "no product cards" asserted as `getByText("product cards").not.toBeVisible()` passes whenever that phrase is simply unprinted, whatever the product does. The semantic weaknesses the findings also name (absence never checked, an assertion a product name satisfies) are the paper's measurement, not a mechanical rule, and stay with the reviewer.

## 10. Fix protocol: follow it for every engine change

1. **Locate the stage and owner** in §2, and read that code.
2. **List every rule and loop control** (§5, §6, §7) that acts on that stage, and read each doc comment.
3. **Prefer changing or removing a rule over adding one.** A new rule needs a stated reason why no existing rule could carry it.
4. **Replay the real ledgers** that showed the problem against the change (they live in `packages/core/.aqa/runs/` and `TestRunApplication/*/.aqa/runs/`). Write a test from the real events.
5. **Check interactions:** run the rule-interaction tests (to be added, §11 step 4).
6. **Update this file** (§3–§9) in the same change.
